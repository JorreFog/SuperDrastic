# G1: GPU 3D renderer (melonDS compute renderer -> GLES 3.1) for 3x/4x

Branch mk4x/G1 (worktree ~/mk4x/wt/G1, from mk4x/integ a122eb7). Setting `render.gpu3d=compute` (default off; only
render.scale 3/4 with the Banana 2D engine; kms.shader forced none while on).

## Design
- melonDS GPU3D_Compute ported: src/gpu3d_compute.{h,cpp}, gpu3d_compute_shaders.h (GLSL ES 310), gpu3d_spans.inc
  (melonDS's span setup verbatim), gpu3d_compute_top.inc (GL table, structs).
- Emu thread at RenderFrame (line 215): VRAM dirty sets + flat VRAM (as Gengis), snapshot of the polygons and their
  vertices (vertex RAM indices) + render registers (meta uniform). Waits only for the previous frame's CPU phase.
- GL thread `bds-gpu3d`, own surfaceless EGL GLES 3.1 context: texture cache (melonDS's, invalidation with the
  snapshot's dirty sets), clear bitmap, span setup, the 10-ish compute passes; the final pass writes melonDS's packed
  u32 (r6|g6<<8|b6<<16|a5<<24) straight into an SSBO in Gengis's quarter-row layout; glMapBufferRange + memcpy into
  one of two row buffers. No pack pass, no glReadPixels.
- Banana 2D engine: SetHires/SetHiresRows (WaitRows waits for the frame's readback): 2D, display capture, presenter
  unchanged. Emulation untouched (renderer only reads GPU3D state).

## HANDOFF (2026-10-26, end of day)
**State:** a working prototype on mk4x/G1 (commits ba00341, f1a941a on mk4x/integ a122eb7), behind `render.gpu3d=compute`
(default off; only 3x/4x with the Banana 2D engine; falls back to Gengis if EGL/GL/shaders fail). Nothing pushed, not
in integ. Device left clean (all runs via mkbench).

**What works:** melonDS's compute renderer runs on the Plus's Mali-G52 (Panfrost, Mesa 25.0.7, GLES 3.1). MKDS race
at 4x renders correctly (LOOKED: ~/mk4x/runs/g1-t1/shots/end-crtc1.png: karts, track, stands, HUD, the countdown
all right). 2D, display-capture path and presenter unchanged. The emulator's thread only snapshots (bds-emu ~5% at
4 fps). kms.shader forced to none, GPU clock held at 800 MHz (kms.gpu_floor_mhz, auto 800; the governor is powersave).

**Numbers (MKDS 4x none, mkbench race):** **4.3-4.4 fps** (software 4x: 41.6; integ: ~47). Per frame: GPU **~205 ms**
(glFinish per pass, render.gpu3d_prof=1: interp spans 49, bin 12.7, sort 0.7, raster 108, depth blend 29, final
5.5), CPU span setup ~10.5 ms, readback 21-22 ms (map + memcpy of 3 MB from the uncached BO: ~140 MB/s). 36.6K work
tiles of 98K allocated (72 MB tile memory at worktiles=8), 1307 polys, 24 variants. First start compiles the shaders
in 12.6 s (Mesa disk cache: 0.17 s later). Temps 49-55 C in those short runs. Not measured: 3+ min thermal, the audio
tap gate (pointless at 4 fps), HG grass, Golden Sun, other picture checks.

**What's broken or unknown:**
1. ~50x too slow on the GPU. g1-t1 (governor floor not set) and g1-t2 (800 MHz) took about the same time, which
   pointed to memory or scratch rather than ALU. But I am not sure g1-t1 really ran at 200 MHz: the launcher may set
   a GPU floor. If both ran at 800, the renderer is simply ALU-bound. The shaders do exact DS integer math per pixel
   (Div64_32_32 with a Newton reciprocal + umulExtended 64-bit emulation in CalcYFactorX, and several Divs per span
   in InterpSpans), likely hundreds of instructions per pixel on a 2-core G52.
2. The readback (22 ms) alone takes more than a 16.7 ms frame. Mapped GPU memory is uncached on Panfrost.
3. shaderdb stats are not captured yet (see the 14:55 entry).

**Exact next steps (in order):**
1. Settle clock vs ALU: run the prof build twice with `BANANADS_KMS_GPU_FLOOR_MHZ=200` and `=800` (same binary). If
   the time scales with the clock, it is ALU.
2. Get spill/instruction stats: in gpu3d_compute.cpp GLInit, `freopen` stderr to /data/mk4x/runs/<tag>/mesa.txt
   (or dup2 to the log fd) before dlopen when render.gpu3d_env is set, then rerun g1-sdb2's command.
3. Cheapest ALU cut: replace Div64_32_32/Div in CalcYFactorX/CalcYFactorY and the XRecip with float
   (or 32-bit-only) division. The factor is 8-9 bits, so float is accurate to about one LSB: a small picture
   difference, LOOK at it. Expect about 2x at best on raster/interp. Even 5x would still be ~40 ms, not 60 fps.
4. Readback: publish rows in bands (map ranges of rows as the final pass finishes, Done per band) so the 2D thread
   starts early, and/or move the memcpy to a second thread. Check whether the device kernel's Panfrost has
   cached/WB BO mmaps (newer kernels). The real fix is no readback: composite on the GPU (G2's territory).
5. **Recommendation:** at today's numbers the compute renderer is not a 60-fps path on a Mali-G52 at 4x. Its design
   (per-pixel exact integer math, tile-sorted work lists) suits desktop GPUs. G2's classic GL renderer uses the
   fixed-function rasterizer and fragment shading that Mali is built for, so it is the more likely winner. Keep G1
   as the reference/fallback, and spend more time on it only if steps 1-3 show a >10x gain within reach. If G2's
   Gpu3DBackend API wins, port this into it: Prepare = the RenderFrame snapshot, GlRender = GLFrame; drop my
   thread/EGL host.
